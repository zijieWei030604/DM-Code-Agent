# 计划与证据协作

## 运行流程

1. 新任务创建独立计划作用域；恢复同一任务则读取 Checkpoint 中的修订历史。
2. ReAct 模型按需调用 `update_plan`，提交完整当前清单。简单任务不必调用。
3. 计划项包含 `id / step / status`；状态为 `pending / in_progress / completed`，最多一项进行中。
4. 工具调用开始时，证据能力捕获进行中的计划项及修订。调用结果通过后置钩子记录。
5. `occurred_during` 只表示动作发生在该计划期间，不表示动作有用、目标完成或因果依据。
6. 模型自己更新计划进度；工具成功、失败、修改文件都不会自动改写清单。
7. 申请完成时，现有门禁独立检查执行证据，计划的 `completed` 不是验收证据。

```json
{
  "plan": [
    {"id": "P1", "step": "定位并确认问题原因", "status": "completed"},
    {"id": "P2", "step": "修复并验证目标行为", "status": "in_progress"}
  ],
  "explanation": "已确认根因，开始修复"
}
```

这是普通工具调用，可使用原生 Tool Calling 或现有 JSON 协议。计划不是新增的独立模型调用。
旧 `enable_adaptive_replanning / max_replans` 参数仍可解析，但不触发独立规划器。

## 历史与上下文

- 同一目标改名或重排时保留 ID；新目标使用新 ID。取消项目从当前清单移除，不伪造 completed。
- 每次有效更新追加 `plan_updated`，不覆盖旧 Trace。无变化提交不增加修订。
- 证据图保留版本化计划节点，已发生的动作仍连接原修订；没有进行中项就不连。
- 最新清单单独存储，每次构造请求时只放一份当前快照；不向历史反复追加状态提醒。
- LCM 可以压缩历史更新过程，但当前快照不依赖摘要恢复，并计入上下文预算。
- Checkpoint 保存完整计划修订与证据图；旧阶段式非空计划不会被猜测转换，恢复时明确报错。
- `evidence_graph_started / evidence_snapshot` 支持多任务及恢复后的读侧图重建，原始事件仍保留。

## 证据边界

`read_before_edit` 表示同文件、同版本的先前读取，不声称它一定是模型决策原因。
`checked_at_completion` 指向完成检查时当前有效的验证记录，包含失败记录，不等于通过认证。
旧版本验证留作复盘，但不作为新版本正确性的证明。

本次不调整门禁强度：保留当前 strict 模式的未验证/无净修改一次提示、直接反证阻断及重复反证终止规则。
关闭证据图不影响计划工具；关闭计划工具也不影响证据检查。
